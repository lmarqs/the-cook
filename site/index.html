Knowledge should be easy to replicate

A team works out how it wants to work in one project: how the code is formatted, which tools run at which version, what a build must pass, how a release is cut, how documentation is organised, how work is tracked and reviewed, how editors and agents are set up. Settling it takes weeks of trying and arguing, and then it works. Then there is a second project, a third, and a new teammate on the first.

Each of those standards ends up in a file some program reads, so the second project gets the standards by copying files. The third gets them from whichever of the two is newer. A month later the team improves one standard, and the improvement goes into one project and no further.

The new teammate clones the first project and finds last month's version of how the team works, and asks. Someone pastes the current files over the old ones to catch up, and the paste takes a colleague's own settings with it. By the end of the year the team's standards exist in ten versions across ten projects, and nobody can say which lines are the standard and which were edited by hand.

Dropping a standard is harder still. Adopting one tool left a line here and a block there, across half a dozen files that belong to other things. When the team moves on from it, nobody remembers every place it touched, and what is not found stays behind.

The lab

A place where standards matter

The standard travels with the code: every clone has it, every branch keeps it, and the next project starts from the same one. Whoever works there, a person through an editor or an agent through its harness, finds the same standard.

Six things hold in the lab, whoever is working and whatever they work with.

  1. 1

    The office: one review

    A person reads every change to the setup before it lands.

  2. 2

    Benches: a working copy each

    Each worker has a place of their own and waits for nobody.

  3. 3

    Suits: nothing crosses over

    One worker's setup does not leak into another's, and the team's own lines stay as they were.

  4. 4

    The board: native files

    Each program reads its own files. Nobody needs Cook to do their work.

  5. 5

    Robot arms: unattended work

    Agents run on their own. A task is done when the team's check says so.

  6. 6

    The conveyor: the setup arrives

    The same setup, at the same version, in every project.

The formula

A standard, written down

A recipe says what a standard puts in a project and where. The team keeps it at a version, and every project applies the same one.

When the team improves a standard, the improvement reaches every project as one diff, and one person reads it before it lands. A copy that falls behind is caught by a check, not by a teammate. A standard the team drops leaves with everything it brought, and nothing else. The team's own lines stay as they were, and each program keeps reading its own files, so nobody needs Cook to follow the standard.

The notebook

A convention no cookbook holds

An organisation has a rule no public cookbook holds. A recipe is a Groovy file in the repository, and Cook treats it like one from a cookbook.

  1. Model what the recipe owns

    A class marked @Ingredient names the files, sections and keys it writes. The rest of every file stays the team's.

  2. Write the recipe

    A few lines that describe themselves in @help, take options with @param and call the model.

  3. Cook it by its path

    No build, no publishing. When another repository wants it, move both files into a cookbook and cook it by coordinates.

~/repo
$ cook recipes/notes.groovy
--- /dev/null
+++ b/NOTES.md
@@ -0,0 +1,1 @@

The cookbook

The recipes that run today, and what each one writes.

cli

The four commands

Four commands and one record of what they wrote.

cook <recipe>...

Cooks recipes left to right in one batch.

cook discard <name>...

Takes out exactly what a recipe put in, without running it.

cook replicate [<name>...]

Rebuilds what the lock records, including ignored output a fresh clone lacks.

cook check [<name>...]

Writes nothing. Exits 1 when the files differ from the lock, 2 on an error.

The CLI reference lists every option.

What runs today

Each recipe says what it writes before it writes it: cook help <coordinates>.

agents#seed

One rulebook for every harness

#seed writes AGENTS.md and a permission policy. #connect renders the policy into Claude Code and Codex, and commits the links, so a fresh clone or a cloud session already has the setup.

agents cookbook

A bench for each agent

Every worktree goes to .worktrees/<branch>, with setup and teardown scripts the team fills in once and every agent runs.

ralph#ralph-tui

Loops that stop at the team's check
