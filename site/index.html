Recipe driven configuration

Cook the best product without any source of contamination.

People and coding agents work in your repository at once, each with their own editor, harness and working copy. Onboard on day one. Work in parallel. Keep your own setup. Carry the recipe to the next repository. As the team grows, the project gets complex and new projects arrive, add a recipe, upgrade it or take it out. Each change is one diff you review, and a recipe taken out leaves nothing behind.

The shift

Onboard on day one. Work in parallel. Make it yours. Do it again.

Four things a repository keeps true for everyone who works in it, person or agent, and that setup copied by hand loses.

Onboard on day one

A fresh clone already has the setup: #connect commits the links each harness reads, and cook replicate rebuilds what git ignores. A newcomer installs Cook and starts; a cloud session starts without even that.

Get started

Work in parallel

Each branch gets a worktree at .worktrees/<branch>, with the setup that branch commits and the setup and teardown scripts your team fills in once. People and agents work side by side without touching each other's files.

git cookbook

Make it yours

A recipe touches only the sections, keys and files it owns. Your theme, model and standing approvals stay in your harness's local file, such as .claude/settings.local.json, merged over the team's settings and kept out of commits.

Sections and markers

Do it again

The setup that worked here is a list of recipes, pinned in cook.lock. Cook the same list in the next repository and it starts where this one is. Change a recipe once and every repository that cooks it gets the change as a reviewed diff.

Cookbooks

The office

Edit the policy, cook, review, commit

One policy file. Three native files. Two harnesses. One question.

  1. Edit what the team decides

    Allow git status and git diff, deny git reset --hard, in .agents/permission/policy.yaml.

  2. Cook and read the diff

    Cook renders the policy into each harness's own files and shows every change, cook.lock included, as one diff. It asks once. A failed write puts the files back as they were.

  3. Commit one change

    The policy and the settings it renders go into one commit, reviewed like any other.

  4. Let CI keep watch

    Cook again and nothing changes. When someone edits the policy and forgets to cook, cook check fails the build.

~/repo
$ cook {{ agents }}#connect --harness=claude
--- a/.agents/adapters/claude/settings.json
+++ b/.agents/adapters/claude/settings.json
@@ -1,8 +1,13 @@
 {
   "permissions": {
-    "allow": [],
+    "allow": [

-    "deny": [],
+    "deny": [
+      "Bash(git reset --hard *)"
+    ],

Contamination

Setup copied by hand drifts

Without Cook

Last month someone allowed git diff for Claude Code. Codex never heard about it, the other repository still has the old copy, and a teammate's hook in the same settings file vanished when a fresh copy was pasted over it.

Now nobody can say which lines are shared setup and which were written by hand.

With Cook

The decision lives in one policy file. Cook renders it into Claude Code's and Codex's own files, marks the part it owns, and leaves every other line alone.

The change lands as one reviewed commit. A recipe you stop using leaves the same way, and takes only what it brought.

The philosophy gives the tenets behind every decision.

The conveyor

Four cookbooks run today

Each recipe says what it writes before it writes it: cook help <coordinates>.

agents#seed · agents#connect

One rulebook for every harness

#seed writes AGENTS.md and a permission policy. #connect renders the policy into Claude Code and Codex, and commits the links, so a fresh clone or a cloud session already has the setup.

agents cookbook

git#worktrees

A bench for each agent

Every worktree goes to .worktrees/<branch>, with setup and teardown scripts your team fills in once and every agent runs.

git cookbook

ralph#ralph-tui

Loops that stop at your check

ralph-tui runs unattended in a worktree of its own. A task completes only when the team's check passes, and clean-up keeps commits that have not landed unless forced.

ralph cookbook

docs#layout

One source of truth for people and agents

The docs-layout skill teaches where a fact goes in docs/, so each fact lives on one page that people and coding agents both read.

The notebook

Write the recipe your team is missing

A recipe is a Groovy file in your repository. Cook reviews, records and checks it like one from a cookbook.

  1. Model what you own

    A class marked @Ingredient names the files, sections and keys it writes. The rest of every file stays the team's.

  2. Write the recipe

    A few lines that describe themselves in @help, take options with @param and call the model.

  3. Cook it by its path

    No build, no publishing. When another repository wants it, move both files into a cookbook and cook it by coordinates.

$ cook recipes/notes.groovy

+++ b/NOTES.md

Procedures

Cook, withdraw, rebuild, check

Four commands, one review, one lock.

cook <recipe>...

Cooks recipes left to right in one batch.

cook discard <name>...

Takes out exactly what a recipe put in, without running it.

cook replicate [<name>...]

Rebuilds what the lock records, including ignored output a fresh clone lacks.

cook check [<name>...]

Writes nothing. Exits 1 when the files differ from the lock, 2 on an error.

The CLI reference lists every option.
