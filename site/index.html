The lab

A place where standards matter

Knowledge should be easy to replicate

Setting up a project is hard. How the code is formatted, which tools run at which version, what a build must pass, how a release is cut, how documentation is organised, how work is tracked and reviewed, how editors and agents are set up: every one of these is a decision, and the team tries and argues for weeks before each settles. Then it finally works. The project feels good to work in, and every part connects like clockwork.

Until a second project arrives, the team improves a standard, a new developer joins, or the team moves on from a tool. Each one unsettles what took weeks to settle.

  1. 1

    One version reaches every project

    ProblemEach of those standards ends up in a file some program reads, so the second project gets the standards by copying files. The third gets them from whichever of the two is newer.

    SolutionA standard still lands in the files each program reads, but it arrives from one place instead of by copy, at one version, in every project.

  2. 2

    An improvement reaches every project

    ProblemA month later the team improves one standard, and the improvement goes into one project and no further.

    SolutionWhen the team improves it, one person reads the change once, and it reaches every project as one change. Whether a project still has the current version is something CI answers with cook update --dry-run, not something a teammate notices months later.

  3. 3

    The current standard is at every seat

    ProblemThe new teammate clones the first project and finds last month's version of how the team works, and asks.

    SolutionA new teammate finds the current standard on the first day, in the project itself, with no older copy to ask about and no catching up by paste.

  4. 4

    What a standard wrote is marked

    ProblemSomeone pastes the current files over the old ones to catch up, and the paste takes a colleague's own settings with it. By the end of the year the team's standards exist in ten versions across ten projects, and nobody can say which lines are the standard and which were edited by hand.

    SolutionWhat a standard wrote is marked, so it is never confused with what a teammate wrote by hand, and nobody's own settings travel to another project with it. The team's own lines stay as they were.

  5. 5

    A dropped standard takes everything it brought

    ProblemDropping a standard is harder still. Adopting one tool left a line here and a block there, across half a dozen files that belong to other things. When the team moves on from it, nobody remembers every place it touched, and what is not found stays behind.

    SolutionA standard the team drops leaves with everything it brought, from every file it touched, and nothing else. Projects read a standard's files without Cook installed, so dropping one leaves no tool behind either.

The recipes

A standard, written down and replicable

Write a standard once. A recipe is a short Groovy file. Cook it into one project or fifty, at the same version, each with its own parameters.

@File
Drops in a whole file. @File(path = 'NOTES.md') String notes()
@Key
Slips one key into JSON, TOML or YAML. Every other key stays put. @Key(path = '.vscode/settings.json', segments = ['editor.formatOnSave']) Boolean formatOnSave()
@Section
Claims a marked corner of a shared file. The rest stays the team's. @Section(path = '.gitignore', id = 'scratch') List<String> ignored()
@Links
Points symbolic links where the standard needs them. @Links(path = '.claude') Map<String, String> links()
@param
Takes --name=value in a recipe. cook.lock remembers it for every later cook. @param(value = 'indent', default = '2') int indent

Hello world: your first recipe

A recipe asks for a model, an ingredient that owns one program's files, and the model says what it writes. Cook writes that and nothing else.

recipes/Notes.groovy
@Ingredient
class Notes {
  private final List<String> lines = [], ignored = []

  void add(String line) { lines << line }
  void ignore(String path) { ignored << path }

  @File(path = 'NOTES.md')
  String file() { lines ? lines.collect { "- ${it}\n" }.join() : null }

  @Section(path = '.gitignore', id = 'scratch')
  List<String> ignoredPaths() { ignored ?: null }
}

The procedures

Cook, update, discard, replicate, check

The commands, and the record of what they wrote.

{% include icons/chef-hat.svg %}cook <recipe>...

Cooks recipes left to right in one batch.

{% include icons/tag.svg %}cook update [<name>...]

Moves recipes to newer releases in their range, as one diff to approve.

{% include icons/trash-2.svg %}cook discard <name>...

Takes out exactly what a recipe put in, without running it.

{% include icons/repeat.svg %}cook replicate [<name>...]

Rebuilds what the lock records, including ignored output a fresh clone lacks.

{% include icons/circle-check.svg %}cook check [<name>...]

Writes nothing. Exits 1 when the files differ from the lock, 2 on an error.

Our cookbook

Batteries included. The recipes Cook ships today, and what each one writes.

The cookbook

Each recipe says what it writes before it writes it: cook help <coordinates>.

agents#seed
agents#connect

One rulebook for every harness

#seed writes AGENTS.md and a permission policy. #connect renders the policy into Claude Code and Codex, and writes links the repository commits, so a fresh clone or a cloud session already has the setup.

agents cookbook
git#worktrees

A bench for each agent

Every worktree goes to .worktrees/<branch>, with setup and teardown scripts the team fills in once and every agent runs.

git cookbook
ralph#ralph-tui

Loops that stop at the team's check

ralph-tui runs unattended in a worktree of its own. A task completes only when the team's check passes, and clean-up keeps commits that have not landed unless forced.

ralph cookbook
docs#layout

One source of truth for people and agents

The docs-layout skill teaches where a fact goes in docs/, so each fact lives on one page that people and coding agents both read.

docs cookbook
